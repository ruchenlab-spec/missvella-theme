## 三、决策记录（ADR）

### D1 · 采用 Shopify CLI 而非 GitHub 自动同步
- **背景**：用户最初询问 GitHub 插件能否自动同步。
- **结论**：以 CLI 为主。GitHub 集成是单向同步（GitHub → Shopify）、push 即部署无质量门禁，且与 CLI 不能混用于同一主题。
- **影响**：发布流程为本地验证 → 安全推送 → live 即时生效。

### D2 · 主题文件集中在 `theme/` 子目录
- **结论**：项目根目录只放开发配置（`.gitignore`、脚本、文档），`theme/` 是唯一上线目录。
- **原因**：避免开发附件（zip、脚本、文档）混入主题上传。

### D3 · 旧版定制主题采用「分层合并」
- **背景**：旧开发包基于较早期 Horizon，310 个文件与新版不同，混有官方版本差异与用户定制。
- **结论**：
  - 第 1 层：旧包独有定制文件（21 个）→ 全部并入；
  - 第 2 层：用户的实质修改（约 5 处手工合并）→ 并入当前新版；
  - 第 3 层：Horizon 官方版本演进（locales、多数 assets js、header/footer liquid）→ 保留新版。
- **判定手段**：schema 设置项差异对比（精确找出被改过的官方文件）+ 定制特征词扫描。

### D4 · 失效资源「先合并，后配置」
- **结论**：合并旧包资源引用（图片/集合/视频）后，在主题编辑器里重新选资源；视频引用会导致模板上传失败，已清空。

### D5 · 圆形集合轮播：放弃原生分组标头，保留原生文本设置
- **背景**：原生 `group` 标头需要静态主题块，而 Shopify 限制「静态主题块不能与 section 本地块混用」（`ValidLocalBlocks`），且 `content_for 'block'` 的 `type`/`id` 必须是字符串字面量，无法动态渲染商家添加的区块。
- **结论**：标头用**自定义 `heading` 区块**，schema 完整复刻原生「文本」区块的设置项，渲染时调用主题原生 `render 'text'`，视觉与交互与原生一致。
- **取舍**：不追求「分组」的多子元素能力，换取「每个圆形可直接在编辑器传图」。

### D6 · 圆形项用 section 本地区块（非 metafield）
- **结论**：每个圆形是一个 `circle_collection` 区块（集合 / 自定义图片 / 自定义视频 / 自定义标题），在主题编辑器里直接配置。
- **放弃方案**：collection_list + 集合元字段（`custom.circle_image`）覆盖——虽然架构更「官方」，但配置入口分散在后台自定义数据里，体验差。

### D7 · 安全推送：只推代码，不推内容
- **背景**：全量 `theme push` 会把本地旧版 `templates/*.json`、`config/settings_data.json` 覆盖到线上，导致编辑器里配置的 Banner/图片丢失。
- **结论**：日常推送仅包含 `assets/ sections/ snippets/ blocks/ layout/ locales/`；改模板结构必须先 pull 线上版本。
- **落地**：`scripts/push-live.ps1`。

### D8 · 不启用本地预览服务
- **结论**：开发者以主题编辑器实时预览为主，不常驻 `shopify theme dev`（会占用端口并创建临时开发主题）。
- **影响**：代码改动通过安全推送同步到 live 主题，编辑器刷新即见。

### D9 · 集合页筛选采用「顶部色板条 + 左侧边栏」统一布局
- **背景**：官方 Filters 区块默认把全部筛选塞进左侧边栏，颜色过多时边栏被拉得很长，与商品网格争夺空间；视觉上也不符合参考店铺的做法。
- **结论**：颜色类筛选提到网格上方做成一排「色卡胶囊」，点击展开该色系的色板面板；其余筛选（价格、尺码等）留在左侧边栏。排序、结果数量与网格密度控件并入顶部条右侧一行。
- **落地**：`blocks/filters.liquid` + `snippets/cf-colour-bar.liquid`（顶部条）+ `snippets/collection-wrapper-styles.liquid`（布局与样式）+ `snippets/cf2-item.liquid` / `snippets/list-filter.liquid`（筛选项渲染）。
- **取舍**：顶部条是集合页专用，不影响搜索页（`search.json`）与其他模板。

### D10 · 颜色分组以商家文本域为唯一来源，内置色卡仅作运行时兜底
- **背景**：主题编辑器里文本域显示的是**已保存的值**，不是 schema 默认值。若把内置色卡写成 schema 默认值，商家不主动粘贴就永远看不到内置分组。
- **结论**：`color_group_map` 文本域为空时，运行时回退到内置色卡标准（`filters.liquid` 顶部的 `color_group_map_value` capture）；一旦商家粘贴自定义分组，即完全以文本域为准。
- **附带**：自定义分组用 `组名:#色值:成员1,成员2` 每行一组的格式。

### D11 · `filters.liquid` 拆分色板条为独立 snippet
- **背景**：`filters.liquid` 的 Liquid 复杂度达 121，超过 theme check 的 120 上限，再加一个 `if` 就会报错。
- **结论**：把顶部色板条（含行为脚本）整体搬进 `snippets/cf-colour-bar.liquid`，block 只保留渲染调用。
- **验证**：抽取前后逐行比对（空白归一化后完全一致），DOM 输出不变。

### D12 · 去除旧品牌痕迹，统一 `mv-` 前缀
- **背景**：主题由旧店铺的开发包合并而来，代码里残留旧品牌的类名前缀、CSS 变量前缀、JS 全局变量名与注释，商家内容里也残留旧品牌文案与外链。
- **结论**：
  - 类名与 API 变量前缀统一为 `mv-`；调色板变量统一为 `--mv-pal-*`（与 `--mv-*` 区分，避免同名冲突）；JS 全局变量去掉品牌前缀。
  - 第三方评价 app 的集成（snippet、模板、header include）**整体删除**。
  - 商家内容里的旧品牌文案替换为本店品牌，旧站绝对链接改为**站内相对路径**（`/policies/*`、`/pages/size-guide`、`/pages/contact`），第三方邮箱改为指向站内联系页。
  - 顺带清理死代码：`mv-shared.css` 删除未被任何标记引用的选择器与 CSS 变量，删除未引用的重复脚本。
- **注意**：内容类改动（`templates/*.json`、`sections/*.json`）**只改本地副本**，按硬性规则不推送；线上对应页面需商家在主题编辑器里同步修改。
